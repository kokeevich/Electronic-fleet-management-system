# Предварительный аудит БД

Источник: предоставленный пользователем SQL-скрипт и существующие модели EF Core.
Живое подключение к SQL Server не проверено: в облачной среде не настроена
FLEET_CONNECTION_STRING. Скрипт не выполнялся. Это аудит описания схемы,
а не подтверждение состояния установленной базы.

## Сопоставление

Все 10 таблиц имеют соответствующие сущности и DbSet. Поля, типы, nullable,
длины строк и связи существующих моделей согласуются с предоставленным DDL.
Имена автоматически созданных PK/UNIQUE в живой БД могут отличаться.

| Таблица | Назначение | Ключи и ограничения |
|---|---|---|
| Roles | Роли | PK RoleId |
| Users | Пользователи | PK UserId, FK RoleId, UNIQUE Login |
| Vehicles | Транспорт | PK VehicleId, UNIQUE LicensePlate и VinNumber |
| Drivers | Водители | PK DriverId, UNIQUE LicenseNumber |
| VehicleAssignments | Закрепления | PK AssignmentId, FK VehicleId и DriverId |
| Documents | Полисы и документы | PK DocumentId, nullable FK VehicleId и DriverId, CHECK типа |
| MaintenanceRepairs | ТО и ремонты | PK WorkId, FK VehicleId |
| Parts | Запчасти | PK PartId, UNIQUE ArticleNumber |
| WorkParts | Состав работ | PK CompositionId, FK WorkId и PartId |
| Notifications | Уведомления | PK NotificationId, nullable FK UserId, CHECK типа |

Даты документов, закреплений и ТО — DATE (DateOnly), суммы — DECIMAL(12,2).
CreatedDate — DATETIME. Каскадное удаление не задано.
DEFAULT предусмотрены для пробега и статуса ТС, остатка запчастей,
срока предупреждения, прочитанности и даты создания уведомления.
Отдельных дополнительных индексов в скрипте нет; PK/UNIQUE создают свои индексы.

## Особенности для следующих этапов

- Страхование хранится в Documents, отдельная таблица полисов не нужна.
- NextMaintenanceDate и NextMaintenanceMileage уже есть в MaintenanceRepairs.
- Таблицы настроек и аудита отсутствуют. Интервал уведомлений можно хранить локально.
- Users.Password содержит открытые пароли в исходных тестовых INSERT.
  До реализации входа нужен переход на солёные хеши (например PBKDF2);
  NVARCHAR(256) позволяет хранить версионированный формат без изменения столбца.
  Исходные INSERT пользователей намеренно не добавлены в Git.
- В SQL есть дополнительная роль «Наблюдатель», которой нет в основной матрице плана.
  Сохраняем её; права определим при реализации авторизации.
- UNIQUE nullable VinNumber в SQL Server допускает только один NULL.
  Для нескольких ТС без VIN впоследствии потребуется фильтрованный уникальный индекс.
- Нет CHECK на отрицательные количества/стоимости/пробег и порядок дат.
  Проверки должны появиться в сервисах соответствующих этапов.
- Documents допускает обе связи одновременно или отсутствие обеих. Для новых
  записей нужно определить владельца в зависимости от вида документа.
- Водительское удостоверение дублируется в Drivers и Documents.
  Для контроля срока водителя используем Drivers, а рассогласование нужно выявлять.
- Нет ограничения пересекающихся закреплений и дублей WorkParts.
- В составе работ нет исторической цены: пересчёт по текущей цене запчасти
  изменит прошлые суммы. Сохранённая MaintenanceRepairs.Cost — источник общей суммы.
- Исходные полисы 2024–2025 годов уже просрочены. Уведомления нельзя показывать
  по готовым текстам «через 30 дней» без пересчёта относительно текущей даты.

## Первый этап

Исправлена ссылка на отсутствующее главное окно и отсутствовавшие обработчики
старых форм. Добавлены MVVM, DI, сервис чтения Vehicles и внешняя настройка БД.
Нет миграций, EnsureCreated, EnsureDeleted или автоматического запуска SQL.
До завершения этапа нужно запустить WPF на Windows, проверить реальное чтение,
недоступную БД и восстановление соединения кнопкой «Обновить».

## Обновление после первого этапа

Пользователь подтвердил проверку первого этапа. Второй этап использует существующие
Users и Roles; строка Password сохраняет имя и длину NVARCHAR(256), но для входа
принимается только версионированный PBKDF2-SHA256 с индивидуальной случайной солью.
Подготовлена утилита tools/PasswordMigration для явного перехода с исходных открытых
паролей. На действующей БД из облачной среды она не запускалась.
Имена ролей проверяются по известному списку; неизвестная роль не даёт войти.
Предусмотренные права будущих операций пока проверены как матрица: соответствующие
операции CRUD будут добавляться и защищаться в сервисах на своих этапах.

## Третий этап

- CRUD Vehicles работает с существующими полями без изменения схемы.
- Уникальность номера и VIN предварительно проверяется запросом; окончательную
  защиту от гонок обеспечивает UNIQUE SQL Server (ошибки 2601/2627).
- Nullable VIN обрабатывается с учётом исходного UNIQUE: только один пустой VIN.
- Перед удалением проверяются Documents, VehicleAssignments и MaintenanceRepairs.
  Если связь появилась одновременно, SQL Server запрещает удаление по FK (547).
- Значения полей Vehicle отмечены как concurrency tokens в EF: WHERE при записи
  проверяет исходные значения без отдельного rowversion-столбца.
- docs/database-demo.sql добавляет новые тестовые логины с PBKDF2-хешами и
  транспорт; ссылки на роли разрешаются по имени, числовые ID не фиксируются.
- Реальная БД в облачной среде не изменялась. Тесты сохранения выполняются
  только на изолированной SQLite; особенности SQL Server требуют проверки пользователя.

## Редактирование остальных реестров

Для Drivers, VehicleAssignments, Documents, MaintenanceRepairs, Parts, WorkParts,
Users и Roles добавлена запись существующих сущностей без изменения схемы.
Сохранение использует транзакцию Serializable и сравнение исходных редактируемых
полей с текущими данными. Роль выполняющего операцию пользователя повторно
проверяется по БД. Пароли пользователей и имена ролей не входят в редактируемые поля.
Пересекающиеся закрепления одного автомобиля или водителя запрещены; границы
периода включены. Для SQL-подключения нужны SELECT и UPDATE на этих таблицах.
Остатки запчастей, общие суммы ТО и дублируемые сведения удостоверений
не синхронизируются автоматически — правила такого учёта требуют отдельной работы.
Уведомления отложены: просмотр/редактирование через сервис недоступны,
но таблица Notifications и её записи сохраняются.
