# Электронная система управления автопарком

Курсовой проект: C#, WPF, .NET 8, Entity Framework Core и SQL Server.
Порядок работы — в [Plans.md](Plans.md), результаты аудита — в
[docs/database-audit.md](docs/database-audit.md).

Первый этап проверен пользователем. На втором добавлены вход по логину и паролю,
сессия, выход и права ролей. В главном окне транспорт отображается карточками ListView.
Добавлена самостоятельная регистрация новых пользователей с ролью «Наблюдатель».
На третьем этапе добавлены поиск и фильтр, карточка, добавление, редактирование
и безопасное удаление транспорта. Палитра — бирюзовая с янтарными акцентами.

## Просмотр всех таблиц

В верхнем переключателе «Раздел» выберите транспорт, водителей, закрепления,
страхование и документы, ТО и ремонты, запчасти, состав работ,
пользователей или роли. Раздел «Подключение» находится в том же списке у администратора.
Разделения на вкладки «Транспорт» и «Реестры» больше нет.
Во всех списках используется общий компактный шаблон карточек ListView.

В разделах доступны поиск по тексту карточки, счётчик записей и кнопка «Обновить».
Редактирование существующих записей доступно согласно роли. Данные загружаются при открытии раздела.
ФИО водителей, названия запчастей и автомобили отображаются через связи БД.
Незаполненные поля подписаны явно; пустая таблица и ошибка загрузки различаются.

Над списком расположена панель действий. Выберите запись и нажмите «Открыть карточку»,
чтобы прочитать полный текст: длинные строки в компактном списке сокращаются.
В карточке просмотра сведения можно копировать, но нельзя менять.
Для подходящих ролей кнопка «Изменить» открывает форму сохранения выбранной записи.
Выбор записи сбрасывается при поиске, обновлении и смене раздела.

Вертикальные отступы общих карточек уменьшены с 18 до 7, расстояние между карточками
с 10 до 5. Шапка и панель поиска также уменьшены; размер основного шрифта сохранён.
На Windows проверьте окно в обычном и развёрнутом состоянии, а также с масштабом
экрана 100% и 150%: поиск, действия и полная карточка должны оставаться доступными.

Пользователи и роли видны только администратору. Пароли и хеши не выбираются
из БД для списка пользователей и не попадают в форму редактирования.
Раздел «Уведомления» исключён из навигации и недоступен через сервис всем ролям.
Его разработка отложена до конца проекта; таблица и существующие записи сохранены.
Наблюдатель не видит пользователей и роли. Доступ проверяется в сервисе.
В составе работ не вычисляется историческая сумма по текущей цене запчасти.

Для проверки достаточно открыть каждый доступный раздел, найти запись по
госномеру/ФИО/названию и проверить список под другой ролью. Для новых таблиц
SQL-подключению нужны SELECT и UPDATE на редактируемые таблицы.
Создание и удаление записей новых реестров в этом шаге не добавлялись;
прежние операции транспорта сохранены.

## Редактирование реестров

Выберите раздел и запись, нажмите «Изменить», исправьте поля и нажмите «Сохранить».
После сохранения список обновится. «Отмена» закрывает форму без записи в БД.
Связанные записи выбираются по названиям из списков; числовые ID вводить не нужно.
Даты вводятся в формате дд.мм.гггг, суммы — с точкой или запятой, до двух знаков.

| Роль | Доступные изменения |
|---|---|
| Администратор | Все восемь реестров |
| Диспетчер | Водители, закрепления, документы |
| Механик | ТО/ремонты, запчасти, состав работ |
| Наблюдатель | Только просмотр |

Проверки прав выполняются в сервисе при загрузке формы и сохранении, включая
актуальную роль пользователя в БД. Если роль изменилась во время сеанса,
редактирование блокируется до повторного входа. Навигация обновляется после входа.
Пароль пользователя не меняется; собственную роль понизить нельзя.
У ролей редактируется только описание: имена закреплены матрицей доступа.

Сохранение выполняется в транзакции. Чужие изменения после открытия формы
не перезаписываются: нужно закрыть её, обновить список и открыть запись заново.
Проверяются обязательность, длины, суммы/количества, порядок дат,
дубли логинов, удостоверений, артикулов и запчастей в одной работе.
Для закреплений принят один водитель на автомобиль и один автомобиль на водителя
в пересекающийся период. Обе границы периода включены.

Полисы и паспорт ТС относятся к автомобилю, водительское удостоверение — к водителю.
Поля удостоверения в Drivers и документ в Documents остаются отдельными записями:
автоматической синхронизации пока нет. Складской остаток и общая стоимость ТО
не пересчитываются автоматически при изменении состава работ.

На Windows с вашей БД проверьте сохранение и отмену в каждом доступном разделе,
смену роли, одинаковые реквизиты, неверные даты и редактирование одной записи
из двух экземпляров приложения. Уведомлений в навигации быть не должно.

Минимальные автоматические проверки нового просмотра:

```sh
dotnet test tests/FleetManagement.Tests/FleetManagement.Tests.csproj --filter "FullyQualifiedName~CatalogEditTests|FullyQualifiedName~CatalogTests|FullyQualifiedName~WorkspaceTests"
```

Это 11 целевых проверок сохранения, валидации, доступа, загрузки и навигации.
Загрузка проверяется на SQLite в памяти; Windows и ваш SQL Server проверяются отдельно.

## Запуск на Windows

1. Установите Visual Studio 2022 с компонентом «Разработка классических приложений
   .NET» и .NET 8 SDK.
2. Используйте существующую базу ozvs_kursach. Файл docs/database-schema.sql —
   справочная копия DDL без тестовых паролей, его не нужно выполнять над готовой БД.
3. Создайте папку %LOCALAPPDATA%\FleetManagement и файл connection.txt.
   Впишите строку подключения одной строкой, например для Windows-аутентификации:

   ```text
   Server=localhost\SQLEXPRESS;Database=ozvs_kursach;Integrated Security=True;Encrypt=True;TrustServerCertificate=False;Connect Timeout=5;
   ```

   Замените сервер на свой. Для учебного локального SQL Server с самоподписанным
   сертификатом допустимо явно поставить TrustServerCertificate=True;
   для удалённого сервера настройте доверенный сертификат.
   Не добавляйте этот файл или пароль в репозиторий.
   Альтернатива — переменная FLEET_CONNECTION_STRING: она имеет приоритет над файлом.
   После изменения переменной перезапустите Visual Studio/приложение.
4. Для старых пользователей с открытыми паролями выполните подготовку ниже,
   либо добавьте готовые тестовые учётные записи через database-demo.sql.
5. Откройте «Курсовой проект.sln», восстановите NuGet-пакеты и запустите проект.

Из PowerShell в папке репозитория:

```powershell
dotnet build "Курсовой проект.sln"
dotnet run --project "Курсовой проект/Курсовой проект.csproj"
```

## Готовые тестовые записи и вход

Откройте [docs/database-demo.sql](docs/database-demo.sql) в SQL Server Management
Studio на том же сервере, к которому подключается приложение, и выполните целиком.
Скрипт использует существующую ozvs_kursach: создаёт недостающие роли,
добавляет четыре новых пользователя и три тестовых автомобиля такси.
Он не удаляет и не перезаписывает существующих пользователей и автомобили.
Повторный запуск пропускает уже имеющиеся логины, госномера и VIN.
Если одно имя роли встречается несколько раз, транзакция отменяется с объяснением.

| Роль | Логин | Тестовый пароль |
|---|---|---|
| Администратор | fleet_admin | TaxiAdmin!2026 |
| Диспетчер | fleet_dispatcher | TaxiDispatch!2026 |
| Механик | fleet_mechanic | TaxiMechanic!2026 |
| Наблюдатель | fleet_viewer | TaxiViewer!2026 |

Это общедоступные учебные учётные записи, предназначенные для тестовой БД.
В SQL хранятся только совместимые PBKDF2-хеши с отдельной солью для каждого пароля.
Их совместимость с текущим AuthenticationService проверяется автоматическими тестами.
Для этих четырёх пользователей запуск PasswordMigration не требуется.
Скрипт не сбрасывает пароль существующего одноимённого пользователя.

Исходные admin/dispatcher/mechanic/viewer содержали открытые пароли в присланном
скрипте. Они не принимаются новой авторизацией до преобразования:
чтобы продолжить использовать именно старые логины, выполните следующую инструкцию.
Скрипт database-schema.sql нужен только для создания новой пустой базы; его нельзя
выполнять повторно над вашей готовой БД.

## Подготовка существующих паролей — один раз

Новая версия принимает только хеши PBKDF2-SHA256 (600 000 итераций, случайная соль).
Логины и пароли для пользователей остаются прежними; меняется только содержимое
Users.Password. Новая БД и новые столбцы не создаются. Открытые пароли не принимаются
даже при правильном вводе, пока подготовка не выполнена.

Утилита предназначена для предоставленного учебного скрипта, где пароли — обычный
текст. Если в вашей БД уже используется иной алгоритм хеширования, не запускайте
преобразование: сначала нужно определить этот формат.

1. Закройте приложение и сделайте резервную копию БД в SQL Server Management Studio:
   база → Задачи → Создать резервную копию → тип «Полная». Сохраните копию вне Git.
2. Используйте ту же настройку подключения, что и для приложения. Для преобразования
   SQL-пользователю нужны права SELECT и UPDATE таблицы Users.
3. В PowerShell из корня репозитория проверьте состояние:

   ```powershell
   dotnet run --project tools/PasswordMigration/PasswordMigration.csproj -- --check
   ```

   Код завершения 1 означает, что есть неподготовленные записи либо ошибка проверки;
   смотрите сообщение. Код 0 — все записи имеют поддерживаемый формат.
4. Для явного применения после резервного копирования:

   ```powershell
   dotnet run --project tools/PasswordMigration/PasswordMigration.csproj -- --confirm
   dotnet run --project tools/PasswordMigration/PasswordMigration.csproj -- --check
   ```

   Преобразование выполняется в транзакции. Уже подготовленные записи пропускаются,
   поэтому повторный запуск не изменяет их. Пароли и хеши в консоль не выводятся.
5. Запустите приложение и войдите с прежними логином и паролем.

Старые версии приложения, сравнивающие открытые пароли, после преобразования
несовместимы с новой БД. Не запускайте повторно исходные INSERT пользователей.

## Регистрация

На экране входа нажмите «Создать учётную запись». Заполните фамилию, имя,
необязательное отчество, логин, пароль и подтверждение пароля.

- Логин: 3–100 символов, буквы, цифры, точка, дефис или подчёркивание.
- Пароль: 8–128 символов; подтверждение должно совпадать, включая пробелы и регистр.
- Новая учётная запись всегда получает роль «Наблюдатель». Выбор привилегированной
  роли при самостоятельной регистрации недоступен. Администрирование ролей —
  отдельный будущий этап.
- После регистрации форма закрывается, а логин подставляется на экране входа.
  Введите выбранный пароль для входа.
- Новые пароли сразу сохраняются как PBKDF2-хеши. Утилита преобразования нужна
  только для старых пользователей с открытыми паролями.

В таблице Roles должна быть ровно одна роль с именем «Наблюдатель» — она уже есть
в исходном SQL-скрипте. Регистрация не создаёт роли автоматически и не меняет схему.
Для подключения приложения нужны SELECT на Users/Roles и INSERT на Users.
Уникальность логина при сохранении обеспечивает существующее ограничение UNIQUE
таблицы Users; правила регистра символов определяются collation SQL Server.

Проверка на Windows с вашей БД:

1. Создайте пользователя с новым логином и войдите. Убедитесь, что отображается
   роль «Наблюдатель», раздел подключения скрыт, транспорт доступен для просмотра.
2. Попробуйте зарегистрировать тот же логин повторно: должна появиться ошибка,
   исходная запись должна сохраниться.
3. Проверьте пустые обязательные поля, короткий пароль и несовпадающее подтверждение.
4. Закройте регистрацию кнопкой «Назад ко входу»: вход должен остаться открытым.
5. При недоступном SQL Server должна появиться понятная ошибка без реквизитов
   подключения. Во время отправки повторная отправка и закрытие регистрации блокируются.
6. После успешной регистрации выйдите и войдите повторно, чтобы проверить сохранение
   пользователя в БД.

## Проверка второго этапа

- Войдите по очереди администратором, диспетчером и механиком; проверьте ФИО и роль.
- Роль «Наблюдатель» сохранена и допускает только просмотр.
- Раздел «Подключение» доступен администратору. Запрос транспорта требует
  действующей сессии и права просмотра в сервисе, независимо от интерфейса.
- Выйдите и войдите другим пользователем: прежняя сессия и введённый пароль
  не должны сохраняться. Закройте окно входа — приложение должно завершиться.
- Проверьте пустые поля, неверный пароль, неизвестный логин и отключённый SQL Server.
  Главное окно не должно открываться; сообщения не должны показывать детали подключения.
- Enter отправляет форму; повторное нажатие во время входа не запускает второй запрос.
- Проверьте карточки ListView, выделение клавиатурой и изменение размеров окна.

Матрица прав находится в AccessService. Чтение и изменение транспорта проверяют
права в FleetService. Регистрация всегда создаёт наблюдателя.

## Проверка третьего этапа — транспорт

1. Войдите диспетчером или администратором. «Добавить» открывает пустую карточку.
   Заполните госномер, марку, модель, год, пробег, статус и VIN; сохраните и
   перезапустите приложение для проверки сохранения в БД.
2. Выберите автомобиль в ListView и нажмите «Открыть карточку». Измените пробег
   и статус. «Закрыть» без сохранения не меняет запись.
3. Поиск работает по госномеру, марке и модели без учёта регистра; он сочетается
   с фильтром статуса. При обновлении списка фильтры сохраняются.
4. Попробуйте пустые обязательные поля, отрицательный/нечисловой пробег,
   год вне диапазона 1900 — следующий календарный год, повтор госномера и VIN.
   Ошибка должна отображаться в карточке без изменения записи.
5. Удалите только ненужную тестовую запись без связей, подтвердив действие.
   Для записи с документами, закреплениями или ТО удаление запрещено;
   вместо него можно выбрать статус «Не используется».
6. Откройте одну запись в двух экземплярах приложения. Сохраните изменения в одном,
   затем попробуйте сохранить старую карточку в другом — должна появиться ошибка
   конфликта. Обновите список и откройте карточку заново.
7. Механик и наблюдатель могут искать и просматривать карточки, но не изменять их.
   Кнопки добавления/удаления скрыты, сохранение недоступно; сервис также запрещает запись.

VIN остаётся необязательным по исходной схеме, однако SQL Server UNIQUE(VinNumber)
разрешает только один NULL. При попытке добавить второй автомобиль без VIN
приложение показывает объяснение. Схема БД на этом этапе не изменялась.
Имена статусов и длина VIN проверяются по схеме: существующие нестандартные
статусы сохраняются, жёсткий формат VIN из 17 символов не навязывается.
Конкурентные UPDATE/DELETE проверяют исходные значения полей, новых столбцов не требуется.

Для работы приложению нужны SELECT на связанные таблицы и INSERT/UPDATE/DELETE
на Vehicles; права ролей внутри приложения проверяются отдельно от прав SQL-подключения.

## Проверка загрузки транспорта после входа

- При корректном подключении список показывает реальные ТС и количество записей.
- При пустой таблице сообщение явно сообщает, что записей нет.
- При отсутствии настройки/недоступной БД окно остаётся открытым и показывает ошибку.
- Исправьте connection.txt и нажмите «Обновить»: данные должны загрузиться без перезапуска.
- Повторное обновление не должно дублировать строки.
- Проверьте изменение размера окна и переключение разделов.

На Linux WPF не запускается. Доступна перекрёстная сборка:

```sh
dotnet build "Курсовой проект.sln" -p:EnableWindowsTargeting=true
dotnet test tests/FleetManagement.Tests/FleetManagement.Tests.csproj
```

Автотесты проверяют хеширование (включая записи из SQL-скрипта), вход, сессию,
ролевую матрицу, подготовку паролей, регистрацию и ViewModel.
Операции сохранения/удаления транспорта, связанные записи и конфликт изменений
проверяются настоящим EF Core на изолированной SQLite в памяти.
SQLite не подтверждает специфические ошибки, collation и выполнение T-SQL на SQL Server.
Запуск окон на Windows и работу с вашей SQL Server БД нужно проверить по инструкции выше.
